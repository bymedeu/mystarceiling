# Development history — 2026-09-13

## Catalogue provenance and identity metadata

**Choices discussed:** reserve Gaia identifier bits for provenance; or preserve
the native `u64` identifier and add separate `u8` metadata. A possible split of
three catalogue-source bits and five classification bits was raised.

**Current status:** separate `u8` metadata is recommended but not yet approved or
implemented. The meaning and taxonomy of “classification,” the bit allocation,
and the in-memory layout remain open.

**Owner's reason:** retaining more source options may be useful if MSC adds
catalogues beyond Gaia and Hipparcos. The owner also wants identifiers excluded
from intensive stellar calculations where practical.

**Trade-off recorded:** one logical byte may consume more space in an
array-of-objects layout because of alignment. A later structure-of-arrays or cold
metadata table could store provenance separately from the calculation loop, but
that remains a measured performance decision.

## Proper-motion propagation

**Choices discussed:** divide the published right-ascension motion by
`cos(declination)` and special-case the poles; apply modulo to the coordinate;
or propagate a three-dimensional tangent vector and wrap right ascension only
afterward.

**Owner decision:** use tangent-vector propagation.

**Owner's reason:** it is the established pole-safe solution and is acceptable
even though the full mathematics is not yet completely familiar to the owner.

**Implementation:** moved source-independent proper-motion and reference-epoch
types from the catalogue layer into the core, grouped the two named components,
and added a pure propagation operation. The operation assumes zero radial motion,
does not use parallax, does not modify `icrs_to_enu`, and is not yet called by the
M1 application. Detailed rationale is in
[the stellar-motion decision](../decisions/stellar-motion.md).

**Validation:** the primary AI inspected and corrected a bounded patch produced
by the secondary `dcodex` account. Corrections made the component names explicit,
separated error reasons, preserved zero-motion inputs, and removed an unsupported
claim of direct ERFA validation. The project then built successfully and all 106
tests passed.

## Propagation logging

**Choices discussed:** per-star debug or trace logging inside the calculation;
or aggregate reporting and sampled failures at the future batch/application
boundary.

**Decision:** keep the core mathematical operation silent. Future bulk code will
own aggregate failure counts and timing; detailed record logs will be sampled or
explicitly enabled.

**Reason:** formatting, synchronization, and output can dominate a loop operating
on millions of stars. Even disabled runtime log calls add a level check to the
hot path. Pure return values also make the operation easier to test and benchmark.

## Owner-approved bounded combined M1 implementation

**Owner decision:** integrate the existing resolved 62-row Hipparcos supplement
with the 4096-row Gaia application prefix; retain the brightest 4096 combined.
Keep source parsers/files separate, native uint64 identifiers with explicit
provenance, and absent Hipparcos BP-RP. This supersedes the pending provenance
status above; the classification taxonomy/bit scheme remains open.

**Owner decision:** apply the existing tangent-vector operation to Hipparcos
J1991.25 directions at J2016 before the fixed Toulouse transform, preserving Gaia
J2016 values. Report propagation failures explicitly at the application boundary.

**Owner decision:** temporarily display only G-like magnitude <=4 after
astronomical visibility, report exclusions, and strengthen brightness contrast.
This is a bounded Toulouse M1 display policy; future automatic visibility is not
implemented. The implementation retains three-pixel points, removes the old
intensity floor, and uses a fixed G=-1.5 white reference. No additional visual or
interactive controls were added.

**Current/local defaults and interfaces:** fixed Toulouse/2016 remains the current
path. Current local time is the approved future time default; an explicit time
without a timezone is UTC. The future default observer and place-name resolution
remain open. This patch adds only the explicit supplement input path to the CLI.
Future CLI/GUI observer, time, and display controls and their division of
responsibilities remain unimplemented/open.

**Implementation details:** a separate catalogue-source enum and optional colour
in `Star`; version/schema 2 binary records preserve both; native source
epochs/directions remain stored and scene propagation is transient. Old binaries
must be regenerated. See
[catalogue integration](../decisions/catalogue-integration.md) and
[M1 behavior and evidence](../milestones/m1-fixed-toulouse-sky.md).

**Validation:** `cmake --build build -j4` and
`ctest --test-dir build --output-on-failure`: 117/117 passed. Real-data execution
retained all 62 Hipparcos stars in 4096, with zero rejected rows/propagation
failures, 720 magnitude exclusions, and 125 screen points. Independent comparison
verified binary selection/order, native IDs/epochs, and Gaia BP-RP. The initial
non-graphical environment could not initialize GLFW; the later successful owner
graphical run and visual review are recorded in the closeout below.

**AI role:** the owner supplied the bounded requirements and authorization. The
secondary AI produced an uncommitted draft; the primary AI reviewed, corrected,
validated, documented, and committed the approved change. No additional owner
motivation is inferred.

## Application controls and repository-local Clang configuration

**Owner decisions:** future time defaults to the current local instant; explicit
timestamps without a timezone mean UTC; invalid supplied values fail. Catalogue
preparation and binary regeneration are explicit operations, not startup work.
No configuration file is needed now. The GUI may use an external library and
should use a collapsible in-window panel, keep the old frame during recalculation
where practical, avoid application restarts, and support full time controls.
Camera orientation stays relative to the local ground when location changes.

**Open questions:** default observer/location acquisition, offline versus online
place-name resolution, optional settings persistence, an additional pointer
gesture for the panel, and the exact control-to-milestone allocation. Camera and
zoom remain M2 recommendations rather than additions to this M1 patch. Full
long-exposure simulation is recommended for M9; an explicitly limited exposure
appearance preview may occur in M2. See
[application controls](../decisions/application-controls.md).

**Clang configuration finding:** the committed `.clang-format`, `.clang-tidy`,
and `.clangd` entries are relative symlinks to the owner's home configuration.
Git pushes only the link text, so this does not upload the target contents, but
standalone clones and CI can receive broken or unintended paths. The agent
recommends keeping canonical files in `~/.config/clang` and synchronizing copies
into each repository so GitHub stores self-contained configuration. No Clang
configuration files were changed in this work.

**AI role:** the secondary AI produced the initial bounded implementation. The
primary AI reviewed its architecture, tests, wording, and repository conventions,
then corrected ambiguous provenance naming, private-header inclusion, fixed-input
wording, and the durable interface decision record.
